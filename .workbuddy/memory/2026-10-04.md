### 取证结论（供复用，别再查第二遍）
**Q1 Tick**
- Tick 由 Update 推进，不是 FixedUpdate：`TimeManager.TickUpdate()` → `IncreaseTick()`（TimeManager.cs:688）。
  累加 `Time.unscaledDeltaTime` 到 `_elapsedTickTime`，while 凑够 `timePerSimulation` 就跑一轮。
- 一轮 tick 顺序（:721-771）：OnPreTick → TryIterateData(读) → PredictionManager.ReconcileToStates()
  → OnTick → Physics.Simulate(tickDelta)（仅 PhysicsMode.TimeManager）→ OnPostTick
  → PredictionManager.SendStateUpdate() → Tick++/LocalTick++。
- 服务器用 `TickDelta`，客户端用 `_adjustedTickDelta`（:693）；服务器每 tick 发 TimingUpdate，
  客户端 `ChangeAdjustedTickDelta` 每次只调 1%（:1130-1140），偏差 > 4 tick 重置。
- `SetTickRate` 注释原文：**TickRate 不同步，必须两端各自设置**（:1228）。→ 项目 50Hz/0.02 硬约束的依据。
- 补帧上限 `_maximumFrameTicks = 3`（:178）。
- PhysicsMode 三档 PhysicsMode.cs:6：Unity=0 / TimeManager=1（本项目）/ Disabled=2。

**Q2 端区分与服务器取输入**
- `IsController => IsOwner || (IsServerInitialized && !Owner.IsValid)`（NetworkObject.QOL.cs:171）。
  → 玩家：客户端独占；球无 Owner，**服务器自己是 Controller**（空 Replicate 走 Authoritative 的原因）。
- 织入入口 `Replicate_Current<T>`（NetworkBehaviour.Prediction.cs:498）：
  Controller → `Replicate_Authoritative`（:518，本地输入 + 存历史 + `toServer: !IsServerStarted`）
  非 Controller → `Replicate_NonAuthoritative`（:598，从 `replicatesQueue` 取网络输入）。两者跑同一个方法体。
- 服务器"接收"靠织入的 RPC reader：`Replicate_Reader<T>`（:968）——只排队不执行；
  校验 `OwnerMatches(sender)`、过期包 early-exit、`> RedundancyCount` 直接 Kick(ExploitAttempt)。
- 项目对照：PlayerPredictedMotor.cs:81/95/130/162。

**Q3 快照下发**

## 追问：契约选择与"加物品"的设计（同日第二轮）

用户问 IReplicateData/IReconcileData/RPC 是什么、事件与持续数据怎么写、后续加拾取物品怎么传、代码怎么维护。
**本轮只给方案与骨架（未落盘文件）**，因为物品模块不在 PROGRESS 排期上，落盘会破坏"一节点一 commit"的节奏，已向用户说明并等待确认。

### 新增取证（FishNet 4.7.3）
- `[ServerRpc]` 默认 `RequireOwnership = true` → 客户端对**服务器拥有的对象**（物品）调用必须写
  `[ServerRpc(RequireOwnership = false)]`，并自己在服务器侧校验（Attributes.cs ServerRpcAttribute）。
- ServerRpc 想拿发起者：声明可选参数 `NetworkConnection conn = null`，codegen 自动填
  （CodeGenerating/Processing/Rpc/RpcProcessor.cs:692 GetNetworkConnectionParameter，要求 HasDefault）。
- `NetworkConnection.FirstObject`（Connection/NetworkConnection.cs:139）= 该连接拥有的第一个 NetworkObject
  = 玩家对象，服务器校验距离用它。
- `[ObserversRpc(BufferLast = true)]` 会把最后一次 RPC 缓冲并在该对象 spawn 时补发给后加入者
  （OnSpawnServer 之前）。**BufferLast 只有 ObserversRpc 有，TargetRpc 没有**。
- `SyncVar<T>`：`.Value`、`.OnChange(T prev, T next, bool asServer)`、`SyncTypeSettings(sendRate=0.1f 默认,
  Channel, WritePermission/ReadPermission)`；默认 `WritePermission.ServerOnly`（客户端改不同步）。
- RPC 参数支持直接传 NetworkObject / NetworkBehaviour（Writer.cs:947 WriteNetworkObject，内部写 objectId），
  但项目惯例传 int objectId（BallImpactData 即如此）。
- 接口签名：`IReplicateData` / `IReconcileData` 都只要 `GetTick/SetTick/Dispose`
  （Runtime/Object/Prediction/Interfaces.cs）；私有的 `_tick` 字段是回滚重放定位历史的索引，必须保留。

### 给出的设计结论（可复用判据）
- 决策顺序：客户端每 Tick → `[Replicate]`；服务器每 Tick 且要回滚 → `[Reconcile]`；
  偶发一次性 → RPC；低频持续状态（非预测对象）→ `SyncVar<T>`。
- 物品拆三条流：存在（服务器 Spawn/Despawn + 池）/ 归属状态（SyncVar<int> 持有者）/
  拾取事件（ServerRpc 请求 → 服务器校验距离 → ObserversRpc(BufferLast) 广播）。
- 后加入者语义：SyncVar 自动补当前值；BufferLast 只补最后一次；**历史序列不重放**
  → "已被谁拿走"必须靠状态，不能靠事件重建。
- 运行时生成的对象（球/物品）不能被场景 UI 直接订阅 → 必须经常驻 GameManager 中转
  （项目已有先例：TappedDispatcher / RoomAnnouncer）。
